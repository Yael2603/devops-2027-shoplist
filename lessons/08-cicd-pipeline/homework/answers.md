# שיעור 8 — תשובות

## 1. מה ההבדל בין CI, Continuous Delivery ו-Continuous Deployment? איפה ה-pipeline שלי עומד?

CI הוא בדיקה ובנייה אוטומטיות של הקוד בכל push. Continuous Delivery מוסיף את ההעלאה של התוצר למחסן, כך שהוא מוכן להתקנה. Continuous Deployment מוסיף גם את ההתקנה עצמה באופן אוטומטי. ה-pipeline שלי בודק, בונה ומעלה ל-ghcr.io לבד, אבל את `helm upgrade` מריצים ביד, ולכן הוא עומד ב-Continuous Delivery.

## 2. ה-runner "ריק" בכל ריצה. שתי דוגמאות לדברים שזה מונע

1. זה מונע "אצלי זה עובד": הבנייה משתמשת רק במה שנמצא ב-GitHub. כשה-Dockerfile שלי היה תלוי בתיקיית `wheels` שקיימת רק במחשב שלי, ה-runner הנקי נכשל וחשף את הבעיה, בעוד שבמחשב שלי היא הייתה נשארת מוסתרת.
2. זה מונע ערבוב עם שאריות מריצות קודמות: קבצים או images ישנים לא יכולים להשפיע על ריצה חדשה, ולכן כל ריצה בודקת ובונה רק את הקוד של ה-commit הנוכחי.

## 3. למה `build` צריך `needs: test`? מה היה קורה בלי זה, אם יש שגיאת תחביר ב-backend?

`needs: test` גורם ל-job `build` לרוץ רק אחרי ש-`test` הסתיים בהצלחה. בלי זה, שני ה-jobs היו רצים במקביל. אם יש שגיאת תחביר ב-backend, `test` היה נכשל, אבל `build` היה ממשיך לבנות ולהעלות ל-ghcr.io image עם הקוד השבור, כי `docker build` לא מריץ את הקוד. הבעיה הייתה מתגלה רק כשה-pod קורס ב-cluster.

## 4. למה ב-`helm upgrade` השתמשתי בתגית של ה-commit, ולא ב-`latest`? שתי סיבות

1. יודעים בדיוק מה רץ: התגית מצביעה על commit אחד שלא משתנה לעולם, ואפשר לפתוח אותו ב-GitHub ולראות את הקוד. `latest` זזה בכל push, ולכן אי אפשר לדעת איזו גרסה רצה.
2. אפשר לחזור לגרסה קודמת: אם גרסה חדשה שבורה, מתקינים את התגית של ה-commit הקודם. עם `latest` זה בלתי אפשרי, כי התגית כבר הועברה לגרסה החדשה.

בנוסף, עם `imagePullPolicy: IfNotPresent`, node שכבר הוריד `latest` ישן לא יוריד את החדש, ויריץ קוד ישן בלי שאף אחד ידע.

## 5. ה-workflow לא מכיל אף סיסמה. איך הוא בכל זאת מצליח להעלות ל-ghcr.io?

בכל ריצה GitHub מייצר אוטומטית מפתח זמני, `GITHUB_TOKEN`, שתקף רק לריצה הזו ורק לריפו הזה. ה-workflow מקבל אותו דרך `${{ secrets.GITHUB_TOKEN }}` ומשתמש בו ב-`docker login`. כברירת מחדל המפתח יכול רק לקרוא, ולכן ב-`ci.yml` הגדרתי `permissions: packages: write`, שנותן לו הרשאה להעלות ל-ghcr.io. כך אין צורך לשמור שום סיסמה בקובץ.

## 6. חברה רוצה להעלות images גם ל-Docker Hub. איפה היא שומרת את הסיסמה, ואיך ה-workflow מגיע אליה?

את הסיסמה של Docker Hub לא כותבים בקובץ ה-workflow, כי כל מי שרואה את הריפו יראה אותה. שומרים אותה ב-Secrets של הריפו: Settings ← Secrets and variables ← Actions ← New repository secret, בשם כמו `DOCKERHUB_TOKEN`. ב-workflow קוראים לה עם `${{ secrets.DOCKERHUB_TOKEN }}`, ו-GitHub מכניס את הערך לפני שהצעד רץ. GitHub מסתיר את הסוד בלוגים (`***`), ואי אפשר לקרוא אותו שוב אחרי השמירה.

## 7. בלוג של ריצה אדומה כתוב `Process completed with exit code 1`. מה זה אומר, ואיך GitHub יודע להפסיק?

כל פקודה מחזירה בסיומה מספר שנקרא exit code: 0 פירושו הצלחה, וכל מספר אחר פירושו כישלון. בד3, `py_compile` מצא שגיאת תחביר והחזיר 1. GitHub בודק את ה-exit code אחרי כל צעד, וכשהוא שונה מ-0 הוא מסמן את הצעד באדום, לא מריץ את הצעדים שאחריו, ולא מריץ jobs שתלויים בו עם `needs`.

## 8. בד5 הרצתי את ה-workflow מהכפתור, בלי commit חדש. למה התגית יצאה זהה לריצה הקודמת? האם זו בעיה?

התגית היא 7 התווים הראשונים של ה-commit. הרצה מהכפתור לא יוצרת commit חדש, ולכן היא רצה על אותו commit ומקבלת אותה תגית. זו לא בעיה: אותו commit פירושו אותו קוד, ולכן אותו image, וה-push רק כותב שוב את אותה גרסה.

## 9. מה עוד עשיתי ביד בד6, שלא היה צריך לעשות ביד? איך הייתי רוצה שזה יעבוד?

בד6 העתקתי ביד את התגית מדף הסיכום של ה-pipeline, והרצתי ביד `helm upgrade` עם `--set` לכל סרוויס. אם אשכח לעשות את זה אחרי push, הקוד החדש יישב במחסן וה-cluster ימשיך להריץ את הגרסה הישנה. הייתי רוצה שגם ההתקנה תהיה אוטומטית: שכלי יזהה תגית חדשה במחסן ויעדכן את ה-cluster לבד. זה Continuous Deployment, ובשיעור 9 נעשה את זה עם Argo CD.
